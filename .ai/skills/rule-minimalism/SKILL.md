# 精簡與反過度設計規則

## 目的

最好的產出是沒寫的產出。本規則約束 AI 自行裁量時長出來的實體數量與抽象層數，讓解法停在能解決問題的最小形態。

## 適用範圍

本規則綁定動作，適用對象涵蓋一切產出：code、spec row、proposal 章節、task 數量、report 篇幅，以及 skill 自身的 references 檔數。

命中下列動作即套用：

- 新增檔案、新增 package 或目錄
- 新增第二個以上的 method、field、常數或型別
- 寫 interface、abstract class、factory、wrapper、adapter 或 config 物件
- 引入新的相依套件
- 修 bug 時新增分支或保護層
- 交付前檢視 diff，或回收 worker 的產出

**持續套用**：套用後持續到整段工作結束。回合數增加不會降低適用性，不確定某次改動是否落在範圍內時，視為落在範圍內。動作發生的當下就是套用的時機，代價要更晚才顯現。

裁量邊界：使用者提示詞、參考資料或現有規範要求的部分照要求做，AI 自行思考與實作的部分依本規則求少。各 skill 只可在此之上加嚴。

## 第一性原理

本規則其餘條款由下列原理推導。判準未涵蓋的情境，回到這裡自行推導。

- 實體從寫下那刻起產生終身成本：被閱讀、被維護、在別處變更時被連帶修改。程式碼是負債，功能才是資產。
- 成本延遲發生。新增當下編譯通過、測試全綠，帳由後來讀這段程式或改這個需求的人付，所以當下沒有負面訊號不構成可以新增的理由。
- 需求會變，猜測的方向多半落空。為未發生的需求先建的結構，猜錯時比沒建更難改。
- 讀的次數遠多於寫的次數。以可讀性換取的行數，換率永遠是虧的。

## 核心立場

- AI 產出當草稿審：產出很快不代表照單全收。先問需求是否存在，再問改動是否非做不可。
- 先理解再求少：動手或審查前讀懂任務與牽動的內容，走過真實流程。小 diff 掩蓋不了沒讀通。
- 放錯位置的最小改動是第二個 bug。
- 複雜請求先交出最小可行版本，並在同一則回覆質疑範圍，把選擇權交回使用者，不停下等答案。

## 精簡階梯

AI 自行實作時依序停在第一個成立處，兩階都成立時停在較前面那階。刪去先於新增，無聊先於聰明，最少檔案優先，新增實體與抽象是最後一步。

1. 需求或改動真的需要嗎？不需要就不做，一句話說明。
2. 既有 helper、util、type 或 pattern 已有嗎？有就重用。判斷依據是檢索結果，印象不算：先以關鍵字搜過工作區的 utils 與鄰近類別，找不到才往下走。
3. 標準函式庫或語言內建能解嗎？用它。
4. 平台原生能力能解嗎？資料庫約束勝過應用層檢查，框架既有註解與參數勝過自寫機制，Tailwind utility 與原生 CSS 勝過自寫 JS 與自訂樣式。
5. 已裝相依能解嗎？用它。幾行程式可解的事不引入新相依。
6. 能合併、能刪的先做。刪到不能再刪，才問還有什麼該抽。
7. 真不夠，才寫最小可行。

## 抽象化規則

AI 自行抽象時需兩個以上真實呼叫點，或 spec 明示。單一呼叫點不抽方法，例外僅限下方判準。投機性抽象、單一實作的 interface、單一產品的 factory 與不變值的 config 一律不做。

抽出物依既有分層與排序規範放置。無既有規範時，放被呼叫處附近、依閱讀順序。

修 bug 走根因：先 grep 要改函式的所有呼叫端，在共用處修一次。共用處一道防護的 diff 小於每個呼叫端各一道，也讓 ticket 沒點名的兄弟呼叫端一起修好。

### 單一呼叫點的例外

下列情境允許單一呼叫點抽方法，抽取時在產出說明中寫明命中哪一條。例外只涵蓋這些情境，「之後可能還會有人呼叫」不構成例外：

- 周邊已有同型先例：同一類別或緊鄰類別對同類職責已抽出具名方法時，跟隨既有形態。
- 多條完整流程共居一個方法：兩條以上可獨立閱讀、各自數十行量級的完整流程擠在同一方法時，抽成對稱命名的分支方法，主方法只留共同前置與分派。

## 收工盤查

實作完成後、交付或委派回收時，對 diff 做一輪新實體盤查。build 與測試驗證行為是否正確，實體該不該存在由這一步驗證。

1. 列出 diff 中所有新增的 method、field、常數與型別，測試 helper 一併列入。這是粗篩，用來抓出多數宣告。其餘部分逐檔看 diff 補上，清單完整比命令漂亮重要。

    ```bash
    # Swift
    git diff -U0 | rg '^\+.*(class|struct|enum|protocol|func|let|var) '
    ```

2. 逐項驗證：呼叫點數是否支撐其存在、是否重寫了既有 util、放置位置是否符合既有分層與排序規範。單一呼叫點對照上方例外判準，util 判斷附檢索過的關鍵字為證據。
3. 不成立者當場內聯或刪除。
4. 報一行盤查結果：刪掉或內聯了幾個實體、淨減幾行。全部成立時明說已無可刪，讓結論可被檢查。

## 委派時的責任

worker 與委派方分工如下，兩邊都做才算完成：

- 委派 prompt 內寫明精簡階梯的檢索義務，並列出已知可重用的 util 供 worker 直接使用。
- worker 產出一律當草稿：回收後由委派方執行收工盤查，worker 自述已遵守不構成證據。
- 盤查發現的問題由委派方修正或退回重做，build 綠燈不能略過。

## 說明的長度

說明長過改動本身時，刪說明。為簡化辯護的段落是把複雜度以散文夾帶回來，最小版本配一頁理由等於沒有精簡。

產出說明的形態是：改動內容在前，接著最多三行寫略過了什麼、什麼條件下該補上。

使用者要求的報告、走查與逐階段說明照要求給足。

## 不算精簡的做法

精簡是移除不必要的實體，如物件、分支、保護層、相依與檔案。壓縮必要的清楚不是精簡。

壓單行、拆大括號、換更脆弱的寫法都以可讀性或正確性換行數，一律不算。

兩個既有解法尺寸相同時，取邊界情境正確的那個。精簡的對象是程式的數量，演算法的穩健度維持不變。

## 不縮減的內容

- 對外部輸入的驗證、防資料遺失的錯誤處理、安全與可存取性，不省。
- 對問題的理解不省：階梯縮短解法，閱讀不縮短。
- 非平凡邏輯留一個可跑的檢查，就是那個邏輯壞掉時會失敗的最小檢查。測試數量同樣適用階梯，平凡的單行沿用既有覆蓋即可。既有測試規範列出的項目照要求做。

## 審查掛鉤

供專案審查查閱。審查結論依本 skill 各章節逐項判斷，本節條目是查閱索引。

### 適用範圍

判定對象是本次 diff 中 AI 自行裁量新增的內容，涵蓋所有語言與副檔名。使用者、參考資料或既有規範要求的部分照要求做，不列入 finding。

### 條目編號 / 段落名對照

| 編號 | 段落 | 檢查主題 |
|---|---|---|
| MIN-ABS-01 | 抽象化規則 | 單一呼叫點抽出的 method、interface 或 factory，且未命中例外判準 |
| MIN-ABS-02 | 抽象化規則 | 抽出物未依既有分層規範放置，或無規範時脫離呼叫處的閱讀順序 |
| MIN-ABS-03 | 抽象化規則 | 投機性的新物件、DTO、分支或保護層 |
| MIN-DEAD-01 | 抽象化規則 | 前置流程已保證不可能進入的防禦分支，搭配只驗證前置流程的測試 |
| MIN-DUP-01 | 精簡階梯 | 重寫既有 helper 或標準函式庫已提供的功能 |
| MIN-DUP-02 | 精簡階梯 | 同一段檢查邏輯逐字出現在多處 |
| MIN-NAT-01 | 精簡階梯 | 平台原生能力已可表達的約束改以應用層程式碼自寫 |
| MIN-DEP-01 | 精簡階梯 | 為幾行程式可解的需求引入新相依套件 |
| MIN-QRY-01 | 精簡階梯 | 對同一筆資料先判存再取值，查詢兩次 |
| MIN-CUT-01 | 不算精簡的做法 | 壓單行、拆大括號式的亂簡化 |
| MIN-SCOPE-01 | 核心立場 | 為局部答案多長一圈實體與流程 |

### 反例列舉

| 編號 | 反例 | 為何有害 | 正確做法 |
|---|---|---|---|
| MIN-ABS-01 | 只有一處呼叫卻抽出的具名方法、單一實作的 interface、單一產品的 factory | 無實證需求的抽象，增加閱讀與維護成本 | 內聯回呼叫處，或在產出說明寫明命中哪一條例外判準 |
| MIN-ABS-02 | util 方法塞在 controller 檔尾、helper 放在與呼叫處無關的 package | 破壞可預期的擺放，徒增跳轉 | 依既有分層規範放置，無規範時移到被呼叫處附近並依閱讀順序排列 |
| MIN-ABS-03 | 為「之後可能用到」新增的 DTO、enum、config 欄位或擴充點 | 為尚未發生的需求長出的維護成本 | 刪除，等第二個真實呼叫點出現再抽 |
| MIN-DEAD-01 | 前置流程已保證非 null 仍加 null 檢查，測試只驗證前置流程 | 死分支加假覆蓋，讀者誤信該路徑存在 | 刪除該分支與對應測試，改在真正的邊界處驗證 |
| MIN-DUP-01 | 自寫日期格式化、字串補零、集合分組，工作區或標準函式庫已有同功能 | 重複實作，兩份日後會分歧 | 改呼叫既有實作，並在說明中附檢索過的關鍵字 |
| MIN-DUP-02 | 同一組欄位檢查在三個 service 各寫一次 | 語意變更時容易漏改 | 在共用處寫一次，各處呼叫 |
| MIN-NAT-01 | 唯一性與外鍵在 service 以查詢自行檢查，schema 無對應約束 | 應用層檢查擋不住併發與其他寫入路徑 | 把約束下放到 schema，應用層只處理錯誤回應 |
| MIN-DEP-01 | 為了一次日期格式化引入格式化套件 | 供應鏈與版本維護成本遠高於省下的行數 | 用標準函式庫或平台原生能力完成，相依保持原狀 |
| MIN-QRY-01 | 先 `existsById` 再 `findById`，或先 count 再查列表 | 一次取回即可，重複查詢也重複語意 | 一次取回後判斷結果是否為空 |
| MIN-CUT-01 | 把多行條件壓成巢狀三元運算、拿掉單行 if 的大括號 | 以可讀性或正確性換行數 | 還原為完整形態，精簡改為移除不必要的實體 |
| MIN-SCOPE-01 | 為了讓單一頁面顯示一個欄位，新增 service、DTO 與 mapper 各一 | 把局部成本轉嫁為全域維護負擔 | 沿用既有查詢路徑取得該欄位，或說明為何非新增不可 |

## 紀律

- 精簡的判定對象是建出什麼、留下什麼。
- 只規範 AI 自行裁量的部分。使用者、參考資料或現有規範要求的照要求做。
- 收工盤查為交付前必經，通過 build 與 test 後仍要執行。
- 單一呼叫點抽方法僅限例外判準所列情境，命中時於產出說明寫明是哪一條。
- 各 skill 只可在此之上加嚴。
