# 文件撰寫規則

## 目的

規範 Galaxy Buds Mac Control markdown 的版面、標點、粗體、終態寫作、完整性與語系對齊，讓每份文件在 GitHub 上呈現一致，讀者拿到的永遠是一份獨立完整的交付文件。

## 適用範圍

撰寫或修改下列檔案時自動套用。敘事型長文同時套用 Skill `/rule-article-humanizer`，表格、欄位字典、code block 與 Mermaid 圖表維持中性技術文體：

- `*.md`
- `Sources/Resources/**/*.md`
- `.ai/skills/**/*.md`

## 通用原則

先讀同目錄的兄弟文章，沿用它們的結構、格式與術語。同一個目錄讀起來像同一位作者寫的，讀者換頁時才不必重新適應。

專屬指令定義了自己的輸出格式時，以該指令為準。

## 標題結構與分隔

標題拓撲由既有文件決定。README、AGENTS、CONTRIBUTING 各有一個 H1，H1 下方接一句用途說明，再以一個 `<br>` 進入第一個 H2。DESIGN 使用 YAML metadata 與單一 H1，章節維持設計系統結構。新增內容沿用檔內層級，既有標題維持原順序。

標題依 H1 → H2 → H3 逐層往下。

多個 H1 的文件，H1 區段之間依序放入空行、三行 `<br>`、兩個空行與 `---`，再接下一個 H1，GitHub 上的區段間距才會一致：

```markdown
# Section A
Content here

<br>
<br>
<br>


---
# Section B
```

同一個 H1 下有多個 H2 時，H2 之間加一個 `<br>`：

```markdown
## Subsection A
Content here

<br>

## Subsection B
```

**H3 以下的細項**：改用 `**粗體標籤**` 接表格、清單或段落。H4 的外觀接近清單項目，讀者容易看錯層級。

同一檔案的 H2 使用同一種語言，新增 H2 時沿用該檔既有語言。模板 code fence 內的 H2 屬於範例字串，依模板需要撰寫。

## 格式慣例

- 比較、屬性與結構化資料使用表格，表格一律有表頭列。
- code block 標明語言，例如 ` ```json `、` ```yaml `、` ```typescript `、` ```bash `，GitHub 才會套用語法高亮。
- 連結寫成 `[顯示文字](path)`，讀者從文字就能判斷連結去向。
- 架構、部署、時序與判定流程使用 Mermaid，圖前先說明權威邊界與讀圖目的。
- Mermaid 層級縮排與文字樹一律使用四個空格。
- 連字一律使用 ASCII 連字號 `-`。破折號 `—` 與 `–` 是 AI 產生的文字最常見的痕跡，改用逗號、句號、冒號或括號。
- 中文散文的句讀依語意關係決定，逐句讀懂再下判斷：
  - 「，」串接同一件事的條件、動作、結果與補充，主題連貫的幾個短句也用逗號接成一句。
  - 「。」用在主題轉換，或主詞不同、各自能獨立成立的陳述。一句串到四五個逗號時，在語意轉折處用句號斷開。
  - 「；」只用在結構對稱、分句內通常已有逗號的並列句（例如「A 時 X，並 Y；B 時 Z，並 W」），以及表格 cell 內的並列項目與互為條件的因果。前後只是相關、結構不對稱時，不用分號。
  - 「、」用在並列的詞或短語。
- 英文依英文標點習慣，semicolon 照英文語法使用，上一條的中文拆句規則只適用於中文。
- 散文中能用中文表達的英文片語，寫成臺灣正體中文。產品名、檔名、程式識別子、協定、標準、enum、yaml 欄位，以及在本 codebase 多檔一致使用的詞屬於技術術語，保留英文。判斷方式：這個詞在 codebase 多檔貫通使用，就是術語；只是描述用的片語，就翻譯。

## 產物與段落邊界

圖、表、code block、編號清單與項目清單都是前文說明的結構化產物。每個產物收束它前面的說明，基本形態是「說明 → 產物」。

產物前的說明交代用途、閱讀方式與判定範圍，產物本身列出完整內容。多個產物時，每個產物與自己的說明組成一個閱讀單元，依閱讀順序交錯排列。產物之後若還有文字，那段文字開啟下一個獨立主題或下一段獨立說明，可以用 H2、H3 標示，也可以直接開新段落。

```text
說明 → 產物
說明 → 產物 → ### 下一個獨立主題 → 新說明
說明 → 產物 → 下一段獨立說明
說明產物 1 → 產物 1 → 說明產物 2 → 產物 2
```

下列排法會讓同一組資訊被拆散，讀者得前後對照才拼得回來，改成上面的形態：

```text
說明 1 → 產物 → 補述說明 2
產物 → 移位的說明 1
說明 1 → 說明 2 → 產物 1 → 產物 2
```

## 粗體使用

粗體只標示結構化標籤，讓讀者掃描時能快速定位欄位。

- **允許的位置**：
  - key-value 清單的欄位標籤，例如 `- **動作**：執行驗證`
  - 清單條款開頭的「：」前標籤，例如 `- **可運作**：value`
  - 段落開頭的「：」前引導標籤，例如行首 `**多選允許**：`
  - 取代 H4 的子標題
  - callout 區塊內的標題
- **其他位置的寫法**：
  - 句內需要強調的詞，用全形引號「X」標示，或直接寫成普通文字
  - 引導句寫成普通敘述句
  - 表格 cell 寫普通文字
  - 整句警告放進 callout 區塊
  - 連結文字與表頭交給 Markdown 本身的樣式
- **判準**：`**X**` 後面緊跟「：」，且接著是該條款的描述，就是標籤位置；其他位置改用「X」或普通文字。
- **狀態與 enum 名稱**：使用行內 code，例如 `running`、`blocked`。

## 終態寫作

每份文件讀起來都是一份獨立完整的交付文件，描述事物現在的樣子。讀者不需要知道上一版長什麼樣子。

- **正文用語**：描述現況。「原本」「之前」「此次修改」「更新為」「調整為」「改為」「原先」「現在改」「AI 調整」，以及英文的「previously」「changed from...to」「this update」「we modified」「AI adjusted」，都是在描述編輯過程，改寫成現況陳述。
- **編輯紀錄**：patch-style diff 描述、inline 版本增量註記、前後比較與 AI 對話痕跡，留在 commit message、PR 與 GitHub Release，正文只寫結果。
- **未完成標記**：`[TODO]`、`[TBD]`、`[placeholder]` 補成實際內容後才交付。
- **同向表述**：寫出正面事實後，直接進入下一個事實。「A，不必 B」「A，不是 B」「只 A，不 B」這類在正面事實後追加否定的補述，以及「不是 A，而是 B」的二元句型，改寫成只陳述 A。否定句只用在三種情況：規則條文本身就是禁令；否定的內容就是行為結果，例如「刪除後無法復原」；省略這句否定，讀者會做出不可逆的錯誤操作。
- **版本型文件**：title-block 的版本行可以記載修訂註記，正文同樣依本章撰寫。

## 完整性

讀者依文件執行時，列出的內容就是全部內容。

- 表格、code block 與清單列出全部項目，每個 DDL 列出全部欄位。
- 列舉寫完整，以省略號、「等」、「etc.」、「and more」收尾會讓讀者以為清單已完整。
- 完整內容過長時，寫出總數並附代表性樣本與註記：「Showing N of M items. Full list available in {location}.」
- 列出受影響檔案時，逐一寫出自專案 root 起的完整路徑，引用 file、class 或 method 時同樣附完整路徑。
- 掃描範圍含平行目錄（兩個語系檔、預覽與實機、Sources 與 Tests 對應）時，每個平行目錄都套用同樣的列表。
- 對清單完整性有疑慮時附註：「⚠️ 上述列表可能不完整。驗證方式：[glob pattern 或 search command]」。
- 執行掃描或列舉任務時，持續到可驗證完整為止，還有能提升完整性的 glob、grep 或讀檔，就執行它。
- 搜尋沒有結果時，至少換一種方式再找（放寬 pattern、搜部分名稱、搜上層目錄、換工具），之後才標為「not found」。
- 重組或重寫既有文件時，新版保留原版全部資訊。刻意刪除的內容，在交付說明中寫出原因。
- 數字只用在有判定意義的地方：門檻（≥ 5、> 70%）、容量上限（context window 1M）、業務硬數字與自然量詞（「一份」「第一個」）。「分四個 namespace」這類只描述清單長度的計數，清單一增減就失真，直接列出內容。

## 翻譯指引（雙語對齊）

可見文字由 `Sources/Resources/en.lproj/Localizable.strings`、`Sources/Resources/zh-Hant.lproj/Localizable.strings` 維護。README、CONTRIBUTING、AGENTS、DESIGN 以臺灣正體中文撰寫，沒有逐段英文鏡像。

- 功能的翻譯資源以正體中文與英文維護，新增可見文字同步檢查兩個語系。
- code block 保持原樣，只翻譯其中的註解與使用者可見字串範例。
- 連結、檔案路徑、i18n 鍵、程式識別子與插值參數名稱保持原樣。
- 譯文依目標語言的語序重寫，句子讀起來像以該語言直接寫成。
- 翻譯完成後執行 `bash test.sh`，驗證配置與協定，另以 `plutil -lint` 檢查翻譯資源語法。

## 常見錯誤

- 根文件的責任與收錄位置依 [docs-entry-policy](references/docs-entry-policy.md) 判定，同一完整事實只在一份文件維護。
- commit 前確認內容已沒有 `[TODO]`、`[TBD]`、`[placeholder]`。
- 規格型文章同時說明「why」與「what」。
- 程式碼範例使用真實可執行的程式碼。

### 反例列舉

- README、AGENTS、CONTRIBUTING 出現第二個 H1，或 H1 下缺用途說明
- 標題從 H1 直接跳到 H3
- 使用 `#### Level 4` 標題
- 同檔 H2 中英混雜，例如 `## Heading Structure` 與 `## 格式慣例` 並存
- H1 之間只有 `---`，缺三行 `<br>`
- 正文出現 `—` 或 `–`
- 連結寫成裸 URL `https://example.com`
- code block 只寫 ```` ``` ```` 未標語言
- 圖、表、code block 或清單後接一段重述產物內容的段落
- 以「說明 1 → 產物 → 補述說明 2」拆開同一組資訊
- 產物所需的說明放在產物後方
- 先集中所有說明，再集中放置所有產物
- 以「；」連接兩個獨立陳述，例如「schema 變動會改變執行計畫；對既有索引欄位之更動會讓 SQL 走錯索引」
- 一整段連續三句以上都以「；」連接
- 同一件事的短句用「。」切開，例如「匯入檔案時先選擇格式。欄位對應依檔案的標題列。預覽區顯示前十筆資料。」
- 英文段落套用中文拆句規則，把合乎英文語法的 semicolon 改成句號
- 散文混入可譯的英文片語，例如「內容以 `semantic commitment` 為主」
- 只描述清單長度的計數，例如「本檔 5 個 question set」「分四個 namespace」
- 句內以粗體強調形容詞，例如 `**必須**附上`
- 表格 cell 內以粗體強調，例如 `| **opus（必選）** |`
- 整句加粗作為警告
- 正文出現「原本」「之前」「此次修改」「更新為」「previously」「changed from…to」「we modified」
- 正文出現 `[TODO]`、`[TBD]`、`[placeholder]`
- 正面事實後追加否定補述，例如「選項取自所選項目，不需要猜」「只在儲存時檢查，不在輸入時檢查」
- 「不是 A，而是 B」句型
- 受影響檔案以 `Sources/Bluetooth/*/` 這類目錄摘要代替逐檔列出
- 列舉以「等」、「etc.」、「and more」收尾
- 表格或 code block 以 `...`、`…` 省略
- 新增功能缺少對應語系文字
- README、CONTRIBUTING、AGENTS、DESIGN 重複維護同一完整事實
- 翻譯改動了連結路徑、i18n 鍵、插值參數或 code block 內容
- 規格文章只寫 what
- 範例程式碼為 pseudocode
