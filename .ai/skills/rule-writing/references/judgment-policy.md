# 判定政策

`scripts/lint.mjs` 列出的發現項目怎麼處理：錯誤怎麼修正、警告與提示怎麼判定、判定怎麼寫、審查回報怎麼列、什麼時候關閉規則，以及怎麼判斷一段文字是否真的有 AI 痕跡。lint 決定要看哪些位置，本政策決定看了之後怎麼下判斷。

## 處理步驟

每筆發現項目依層級處理。警告與提示的判定以發現項目附的判斷路徑為起點：

1. 錯誤：依改法修正。用語的一對一錯誤可以加 `--fix` 直接取代。
2. 警告：先讀參照指向的條目檔，看成因與改寫前後對照，再回答判定問題。答案寫在依據的開頭。
3. 提示：讀過判定問題與參照後自行決定要不要改。決定不改時可以不填判定。
4. 改寫後重跑 lint，確認改寫沒有引入其他規則的發現項目。
5. 以 `--judged` 確認全部處理。

## 判定的寫法

判定問題的答案「是」表示違規。判定與依據寫在 `lint.json` 的 `verdict` 與 `basis`，依據以判定問題的答案起頭，接著寫這一句的具體情況，例如「否，這個粗體在表格第一格，是列的標籤」：

| 判定 | 依據的開頭 | 理由寫什麼 | 之後要做的事 |
|---|---|---|---|
| 違規 | 是 | 這句符合判定問題描述的情況 | 依改法改寫 |
| 誤報 | 否 | 這句不屬於該規則的原因，例如被討論的寫法、規則條文本身的禁令、產品介面的文字 | 保留原文 |

## 審查回報

審查文字時，每一筆違規引用條目編號與參照，再附改法，例如 `DOC-FMT-05` 與 `references/writing/format-markdown.md#中文句讀`。條目編號從 `references/tables/rule-index.tsv` 查出，引用條目的檢查主題要與觀察相符。檢查主題都對不上的觀察另列為建議，並寫出理由。

## 關閉規則

文風調整後某條規則在這份文字仍然不適用時，以 `--off 規則=理由` 關閉。理由寫出這份文字的性質與規則不適用的原因，例如「錯誤碼表的說明欄，被動結尾是欄位慣例」。理由寫進 `lint.json`，`--judged` 列出全部關閉的規則，審查時看得到。一份文字裡只有少數位置不適用時，逐筆判為誤報。

## 判斷是否為 AI 痕跡

改寫前先判斷這段文字是否真的有 AI 痕跡。判斷看模式群聚：單獨一個破折號、一個「此外」或一句短句都沒有意義，破折號加上硬湊三項、宣傳形容詞與公式化結論的組合，才是明確訊號。lint 列出的警告與提示是待判定的位置，判定時依這一節決定是違規或誤報。

下列特徵單獨出現時，不足以判定為 AI 痕跡：

| 特徵 | 理由 |
|---|---|
| 語法完美、風格一致 | 專業寫手與經過編輯的文章本來就是這樣 |
| 口語與正式語氣混雜 | 技術背景的作者常這樣寫 |
| 平淡、乾燥的敘述 | AI 痕跡有特定形態，乾燥只是一種寫法 |
| 正式或學術詞彙 | AI 過度使用的是語言與語法條目列出的特定詞，專業詞彙本身是正常用語 |
| 書信體開頭或結尾 | 問候語與署名是正常的書信慣例 |
| 單獨一個連接詞 | 「然而」「因此」堆疊出現時才是訊號 |
| 單獨一句短句 | 人也會用短句強調重點，連續堆疊才是斷奏腔 |
| 沒有附來源 | 多數內容本來就沒有引用 |
| 複雜而正確的排版 | 範本與編輯器本來就能產出乾淨版面 |
| 引用或範例中的模式詞 | 被討論的詞是對象，寫在「」或 code span 內，lint 遮罩這兩種寫法 |

下列訊號代表真人寫作，改寫時保留：

- **具體、罕見、難以捏造的細節**：一個真實的錯誤代碼、一段奇怪的 log、「那台只在週一早上會掉線的掃描槍」。
- **矛盾情緒與未解的張力**：「整體是好的，但它讓我有點不安，我說不清為什麼。」
- **帶時代印記的用語**：特定年份、特定團隊才懂的說法。
- **作者能解釋的用字選擇**：作者說得出「為什麼用這個詞」。
- **句長變化豐富**：長短句交錯。
- **插話、括號旁白與自我修正**：「（我一直想寫『幾乎』，但這件事其實是確定的。）」
