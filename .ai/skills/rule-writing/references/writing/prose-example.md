# 完整範例

一篇技術部落格式的敘事文章，從充滿 AI 痕跡的原文，經過草稿、覆核到定稿。改寫自 `blader/humanizer` 的旅遊隨筆範例，場景換成效能調校。

## 改寫前

```text
我最近花了五天深入探索了某個開源專案的效能調校，這段經歷可以說徹底改變了我對系統優化的看法。從第一次執行 benchmark 的那一刻起，我就知道這是一次意義非凡的旅程。

作為現代分散式系統演進的一個生動證明，這個專案巧妙地融合了快取策略、非同步處理與精密的資源調度，展現出令人驚豔的工程巧思。是的，除錯過程頗具挑戰性——我的耐心確實受到考驗！——但每一次深入追查都帶來令人振奮的洞見，讓一切努力都值得。

沒有一次效能調校是完整的，除非跑過完整的 profiling 流程。而結果呢？簡直令人拍案叫絕。找到那個 N+1 查詢的瞬間，是我永遠不會忘記的時刻。

但真正讓這次調校特別的，不只是數字上的改善——而是那種感覺。稍微深入程式碼底層，你會發現一個更安靜、更真實的世界：精心設計的抽象層、優雅的錯誤處理，以及邀請你放慢腳步、細細品味每一行程式碼的架構決策。

當然，最終那份效能報告揭示了驚人的改善幅度。排查過程可能漫長，但這番經歷對任何工程師或好奇的技術愛好者而言，絕對值回票價。

我還會再做一次嗎？當然會。這不只是一次效能調校——這是一段值得反覆回味的旅程。如果你正夢想著下一次系統優化，這絕對是一次能留下永恆回憶的挑戰。✨
```

## 草稿

```text
我上個月花了五天調某個開源專案的效能，到現在心情還有點複雜。系統確實變快了，過程卻比我預期的折騰。

快取層是個大問題。設定檔看起來乾淨，每改一個參數就要重跑一次完整測試，一次十分鐘。第二天我已經在想辦法縮短這個迴圈。

我照文件建議用了官方的 profiler。畫面很擠，大部分時間都在看同一組呼叫堆疊。真正有用的是我自己加的計時 log，它抓到一個藏在迴圈裡的重複查詢。

我最喜歡的是離開主要路徑之後看到的東西：錯誤處理、邊界條件，還有那些看起來不起眼、卻撐住整個系統的小函式。這些才是我後來一直在想的部分。

效能報表的數字很漂亮，我卻花了更多時間在調報表格式。

我還會再做一次，下次會先把 log 系統搭好。
```

## 覆核：這段為什麼還像 AI 寫的

- 草稿比原文少了很多細節，是把細節刪掉，沒有把細節重新組織。
- 有些句子收得太整齊，例如「系統確實變快了，過程卻比我預期的折騰」，少了真實猶豫的痕跡。
- 結尾平淡、通用，不像同一個作者會寫的結尾。

## 定稿

```text
我上個月花了五天調某個開源專案的效能，到現在心情還是有點矛盾。變快了，沒錯。但比任何人事先告訴我的都更折騰。

快取層是整件事的核心，卻從頭到尾沒人提醒過我。設定檔看起來很乾淨，改一個參數就等於重跑一次完整測試，一次十分鐘。第二天，我已經開始想辦法縮短這個回饋迴圈，聽起來有點本末倒置，但大概也是老實的做法。

大家都說用官方 profiler，我也照做了，結果畫面塞滿呼叫堆疊，三個模組都指向同一段程式碼。下次我會先加計時 log。那個藏在迴圈裡的重複查詢，我是在一個不起眼的分頁函式裡找到的，靠的就是一行土法煉鋼的 log，找到的那一刻確實值得。

我沒預期到的是，離開主要路徑之後，這個系統安靜得多。往下走兩層，看到的是仔細寫的錯誤處理、清楚的邊界條件，還有一群老工程師留下的小函式，看起來不起眼，卻撐住整個系統。後來我一直在想的，是這些小函式。

報表的數字很漂亮，格式也整齊，我卻把大半時間花在調格式上。如果只有兩天，我會把畫報表的時間拿去多讀一輪那些小函式。

我還會再做一次，下次先把 log 系統搭好。這個專案對新人不太友善，我猜這也是它讓人願意花時間搞懂的原因，雖然搞懂的過程讓人有點惱火。
```

## 定稿做了什麼

保留第一人稱回顧與原文的細節密度，移除聊天式開場、意義渲染、宣傳語、刻意的熱情、破折號、三段式節奏、樂觀結尾與表情符號，改用具體的摩擦點、矛盾情緒、長短不一的句子與真實場景重新組成整篇文章。
