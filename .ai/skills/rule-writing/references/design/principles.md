# 設計原則

寫作檢查的總則：lint 與 LLM 怎麼分工、規則怎麼分層級、每筆發現項目帶什麼資訊、規則依哪些面向套用，以及規則寫在哪裡。維護機讀定義表與引擎時依這些原則判斷。

## 分工

lint 決定要看哪些位置，LLM 決定要不要改。寫作規則多半寫不成精確的條件，同一個「；」在對稱的並列句是正確的，在兩個獨立陳述之間是黏接。lint 擅長找出所有可能的位置，不漏看，LLM 擅長讀上下文判斷這一處屬於哪一種。兩者分開後，lint 的條件可以寫得寬，判斷交給讀得懂語意的一方。

## 層級

一條規則的層級依 lint 判得多準而定。層級寧可放低：誤判成錯誤的規則會讓 LLM 把合理的寫法也改掉，放成提示最多是多讀一筆。規則的層級依語料量測決定，方法見 [amendment](amendment.md)。各層級放的規則如下：

| 層級 | 什麼規則放這裡 | 讀者看到時 |
|---|---|---|
| 錯誤 | 命中就是違規，程式能精確判定，例如破折號、未完成標記、只有一種台灣說法的大陸用語 | 直接修正 |
| 警告 | 命中多數是違規，但要讀上下文才能確定，例如否定補述、句中粗體 | 回答判定問題後決定 |
| 提示 | 命中多半是合理的寫法，少數是違規，例如被動結尾、技術文字中的分號 | 知道有這個位置，自行決定 |
| 關閉 | 這份文字不適用 | 不輸出 |

## 判斷路徑

只告訴 LLM「這裡有粗體」，它會以為全部都要改。每筆發現項目附三樣東西，讓 LLM 知道為什麼列出、怎麼改、去哪裡讀完整說明，程式能精確判定的規則沒有判定問題，只附改法與參照：

- 判定：一個是非問題，答案「是」表示違規。問題寫的是違規的情況，例如「這個粗體是在句中強調一個詞，而不是區塊開頭的標籤嗎？」。
- 改法：判為違規時的改寫方向。
- 參照：條目檔與標題，有成因與改寫前後對照。

## 三個面向

規則依格式、版面與文風套用，lint 不預設文字是 Wiki 或 markdown：

- 格式決定 markdown 的規則套不套用。commit message、PR 描述與對話段落是純文字，只套用行文的規則。
- 版面決定 Wiki 的標題、分隔與 `.order` 規則套不套用。
- 文風決定各規則的層級。文風依寫作目的分類，對應 Diátaxis 的教學、操作指南、參照與說明，另加敘事。一個文風是一組層級覆寫，不另寫規則，同一條規則在教學文降為提示，在技術文件維持警告。

## 規則寫在表

規則、層級、判定問題、改法、偵測詞、正規式、成對連接詞、門檻、文風、路徑設定與 markdown 寫法都寫在機讀定義表，人與 lint 讀同一份資料。程式只實作機制：解析、遮罩、比對、層級的計算與輸出。程式不寫死詞與判斷，不為特定文件、特定句子寫分支。由程式判定的規則（例如標題跳級）在程式裡只有規則名稱，條目、層級、說明、判定問題與改法仍取自規則表。

## 被討論的寫法

文件常常需要寫出被討論的寫法，例如條目檔的反例、介面上的按鈕文字。這些寫法寫在「」或 code span 內，lint 檢查前遮罩，就不會把它們當成正文的用詞。被遮罩的範圍見 [engine](engine.md)。
