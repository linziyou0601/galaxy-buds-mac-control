# 文件與行文撰寫規則

## 目的

規範文字怎麼組織與句子怎麼寫：版面依文字所在的位置與格式，讀者拿到的永遠是一份獨立完整的交付內容，文字讀起來像熟悉這個領域的人親手寫的。

語言模型依統計挑選最可能出現的字詞，產出容易趨向平均值：同樣的句型、同樣的連接詞、同樣的補述習慣。本規則把這些平均值痕跡寫成可檢查的模式。`scripts/lint.mjs` 找出要看的位置並說明為什麼列出，LLM 判定要不要改，並示範人會怎麼寫。

## 適用範圍

任何要交給讀者的文字都套用：文件、文章、報告、交接、README、skill、程式註解、commit message、PR 描述、介面文案與對話中要交付的段落。每段文字依格式、版面與文風三個面向決定套用哪些規則、層級多高：

| 面向 | 決定什麼 | 來源 |
|---|---|---|
| 格式 | markdown、mdx 或純文字。code block、連結、粗體與產物的規則只套用在 markdown 與 mdx | 副檔名，見 `references/tables/layout-formats.tsv`。commit message、PR 描述與對話段落以 `--text` 當成純文字 |
| 版面 | 是否採 Azure DevOps Wiki 版面。採用時另外套用 TOC、標題分隔與 `.order` 的規則 | 路徑，寫在專案定義表的 `layout-profiles.tsv`，以 `--project` 傳入 |
| 文風 | 文字的寫作目的，每個文風調整一組規則的層級 | 專案定義表依路徑給預設文風，文件以 front matter 或 HTML 註解宣告，命令列以 `--style` 指定 |

文風依文字要讓讀者做什麼來選，一份文件可以宣告多個文風，依序套用：

| 文風 | 用在 | 調整 |
|---|---|---|
| 技術 | 預設。操作指南、概念說明、README、報告、交接、skill 與程式文件 | 不調整，各規則依預設層級 |
| 教學 | 帶讀者一步一步完成第一次操作的教學文與新手導覽 | 給讀者的否定提示（例如「不必記指令」）降為提示 |
| 敘事 | Launch Note、Feature Story、上線公告、部落格、提案說明動機與取捨的段落 | 關閉修飾語，口語開場、二元句型與否定補述降為提示，中英夾雜與公文腔升為警告 |
| 參照 | 欄位字典、對照表、錯誤碼表這類以表格與清單為主的文件 | 關閉被動結尾、否定補述、分號、符號代替文字、中英夾雜與列舉省略 |
| 關閉 | 不由本 skill 檢查的文件，例如受控語言的永久規格 | 關閉全部規則 |

文風宣告的寫法：

```markdown
---
writing-style: 敘事
---

<!-- writing-style: 參照 -->
欄位字典的段落，套用到下一個同級以上的標題
<!-- writing-style: end -->
```

## 專案慣例

修改內容前先讀 [project-policy](references/project-policy.md)，確認本專案的版面、文件分工與翻譯方式，再依規則型錄撰寫。專案明定的格式優先於型錄的通用預設。

## 通用原則

先讀同目錄的兄弟文章，沿用它們的結構、格式與術語。同一個目錄讀起來像同一位作者寫的，讀者換頁時才不必重新適應。專屬指令定義了自己的輸出格式時，以該指令為準。

## 核心原則

1. **直接進入內容**：段落第一句就是資訊。開場暖場句、強調性的拐杖詞拿掉後，讀者更快讀到重點。
2. **同向陳述**：寫出事實，接著寫下一個事實。「不是 A，而是 B」、正面事實後追加的否定補述、戲劇性的分段鋪陳，都讓文章讀起來像套模板。
3. **句長有變化**：短句與長句交錯，清單的項數跟著內容走。每句長度與結構都相近，是統計平均值最明顯的痕跡。
4. **信任讀者**：直接陳述事實。軟化語氣、預先辯解與逐步引導，會讓讀者覺得被當成新手。
5. **具體勝過漂亮**：讀起來像能單獨截圖引用的金句，通常犧牲了精確度，改寫成具體陳述。

### 改寫保留資訊量

改寫覆蓋原文的全部內容。原文五段，改寫後仍是五段量級的資訊密度，拿掉的只有空洞修辭。

### 語氣校準

使用者提供自己的寫作樣本時，先讀樣本：留意句長、用詞層級、段落開場、標點習慣、慣用詞與過場方式，改寫時貼著樣本的語氣寫。樣本寫「東西」就寫「東西」，樣本寫短句就寫短句。沒有樣本時，敘事段落依下一節的預設語氣，技術文字依技術文體。

### 敘事段落的作者語氣

敘事段落背後要有一個真實的人。去掉 AI 痕跡之後，文字若變得整齊卻沒有聲音，讀者同樣認得出來。作者在素材中表達過的觀點、猶豫與情緒，改寫時要寫出來：讓句子帶著作者對事實的反應，讓短句接一句需要時間展開的長句，保留離題、旁白與自我修正。觀點與第一人稱經驗只能來自作者已表達過的內容。技術文字與參照文風的表格、條款與說明欄維持中性，寫成精確的直述，作者語氣只用在敘事段落。

改寫前（整齊但沒有聲音）：

```text
這次實驗產生了有趣的結果。Agent 寫出了三百萬行程式碼。部分開發者印象深刻，部分則持保留態度。實際影響仍不明確。
```

改寫後（作者在場）：

```text
我真的不知道該怎麼看這件事。三百萬行程式碼，多半是在人類大概都睡了的時候產生的。開發社群一半人驚呼，另一半人在解釋為什麼這不算數。真相可能落在無聊的中間地帶，但我一直在想那些整夜運轉的 Agent。
```

| 組 | 涵蓋 |

## lint 檢查

lint 決定 LLM 要看哪些位置，LLM 決定要不要改。每筆發現項目附三行判斷路徑：判定是一個是非問題，答案「是」表示違規。改法是判為違規時的改寫方向。參照指向條目檔的標題，那裡有成因與改寫前後對照。只讀發現項目的說明就動手改，容易把合理的寫法也改掉，判定前先讀參照。每筆發現項目的層級決定處理方式：

| 層級 | 意思 | 處理 |
|---|---|---|
| 錯誤 | 程式能精確判定的違規，例如破折號、未完成標記、大陸用語 | 依改法修正，有錯誤時結束代碼為 1 |
| 警告 | 寫得出觸發條件，要讀上下文才能判定 | 回答判定問題，答案寫在依據的開頭。「是」時判為違規並修正，「否」時判為誤報並寫出理由 |
| 提示 | 常見但多數時候合理的寫法，例如被動結尾、技術文字中的分號 | 讀過後自行決定要不要改 |

規則、層級、判定問題、改法、偵測詞、正規式、文風與路徑設定寫在機讀定義表 `references/tables/*.tsv`，清單見 [tables-catalog](references/tables-catalog.md)。lint 的模組、指令、輸出與結束代碼見 [scripts-contract](references/scripts-contract.md)，遮罩、文風、層級的計算與檢查範圍見 [design/engine](references/design/engine.md)。文風調整後某條規則在這份文字仍然不適用時，以 `--off 規則=理由` 關閉並寫出理由，理由寫進 `lint.json`，審查時看得到。lint 的指令如下，`--root` 傳儲存庫根目錄，`--project` 傳專案定義表目錄，傳法寫在各儲存庫根目錄的 `AGENTS.md`：

```bash
node {skill 目錄}/scripts/lint.mjs {路徑}... --root {儲存庫根目錄} --project {專案定義表目錄} --out {輸出目錄}
node {skill 目錄}/scripts/lint.mjs --text "{commit message 或 PR 描述}"
node {skill 目錄}/scripts/lint.mjs --judged {輸出目錄}
```

## 寫作流程

撰寫或改寫文字時依下列步驟前進，審查從第 4 步起執行：

1. 先讀同目錄的兄弟文章，確認格式、版面與文風。文風不是路徑給的預設時，在 front matter 或章節開頭宣告。
2. 依 [writing-catalog](references/writing-catalog.md) 的版面、格式與交付內容組排版面、產物與段落，依行文組與核心原則寫句子。
3. 改寫整篇敘事文章時，可以先寫草稿，自問「這段為什麼還像 AI 寫的」，列出殘留破綻後再定稿，完整流程示範見 [prose-example](references/writing/prose-example.md)。
4. 交付前執行 `scripts/lint.mjs {路徑}... --root {儲存庫根目錄} --project {專案定義表目錄} --out {輸出目錄}`，依改法修正全部錯誤。用語的一對一錯誤可以加 `--fix` 直接取代。
5. 在 `{輸出目錄}/lint.json` 逐筆處理警告：讀參照，回答判定問題，依 [judgment-policy](references/judgment-policy.md) 填寫 `verdict` 與 `basis`，判為違規時依改法改寫。提示讀過後自行決定。改寫後重跑第 4 步。
6. 以 `scripts/lint.mjs --judged {輸出目錄}` 確認全部處理，再依「驗收條件」檢查語意層的條目。

## 驗收條件

交付的定稿達到下列條件：

- `scripts/lint.mjs` 沒有錯誤，`--judged` 的結束代碼為 0，關閉的規則都寫了理由。
- 每一處命中型錄模式的句子都已改寫，改寫後的句子沒有引入其他模式。
- 唸出來自然，句長有變化，用具體細節取代模糊主張，能用「是」「有」的地方就用「是」「有」。
- 重讀一次，找不到一看就像 AI 寫的地方。

## 審查掛鉤

審查型 skill 以條目編號引用本 skill 的規則。條目編號、段落、參照與檢查主題寫在 `references/tables/rule-index.tsv`，審查結論依參照的條目檔逐項判斷，審查時以 `scripts/lint.mjs` 的發現項目為起點。各路徑採用的版面與文風寫在各儲存庫的專案定義表的 `layout-profiles.tsv`。

### 反例列舉

- 採 Wiki 版面的文件在第一個標題之前缺 `[[_TOC_]]`，標題從 H1 直接跳到 H3，使用 `#### Level 4` 標題
- 同檔 H2 中英混雜，例如 `## Heading Structure` 與 `## 格式慣例` 並存
- 採 Wiki 版面的文件在 H1 之間只有 `---`，缺三行 `<br>`
- 正文出現 `—` 或 `–`，連結寫成裸 URL `https://example.com`，code block 只寫 ```` ``` ```` 未標語言
- 圖、表、code block 或清單後接一段重述或補述產物內容的段落，例如「說明 1 → 產物 → 補述說明 2」
- 產物所需的說明放在產物後方，或先集中所有說明再集中放置所有產物
- 以「；」連接兩個獨立陳述，或一整段連續三句以上都以「；」連接
- 同一件事的短句用「。」切開，例如「點擊儲存。系統驗證。驗證通過。資料寫入。」
- 英文段落套用中文拆句規則，把合乎英文語法的 semicolon 改成句號
- 散文混入可譯的英文片語，例如「main agent 依 disposition 選一動作」「範圍標為 whole-file」
- 句內以粗體強調形容詞，例如 `**必須**附上`，或表格第一格以外的格子以粗體強調
- 中文與英文、數字之間沒有空白，例如「在LeanCloud上」「花了5000元」，或全形標點前後加空白
- 專有名詞寫錯大小寫，例如「github」「MacOS」，或使用「h5」「nextjs」這類不道地的縮寫
- 正文出現「此次修改」「現在改」「previously」「changed from…to」「we modified」
- 正文出現 `[TODO]`、`[TBD]`、`[placeholder]`
- 受影響檔案以 `libs/plugin-*/` 這類目錄摘要代替逐檔列出，列舉以「等」「etc.」「and more」收尾
- 中英版本 H1、H2、H3 數量不一致，翻譯改動了連結路徑或 code block 內容
- 採 Wiki 版面的文章未加入 `.order`
- 句中出現「標誌著……關鍵時刻」「見證了……的演變」「彰顯其重要性」
- 句尾加上「……反映了團隊對品質的重視」這類補述式分析
- 非行銷文件出現「強大的」「無縫整合」「一站式」「極致體驗」
- 「業界普遍認為」「專家指出」卻沒有來源
- 文末出現「儘管面臨挑戰，仍持續發展」的收尾段
- 一段內疊用「此外」「至關重要」「值得注意的是」兩次以上
- 用「作為……的核心」取代「是」
- 「不是 A，而是 B」「不只是 A，更是 B」「不處理 A，只負責 B」「只在儲存時檢查，不在輸入時檢查」
- 正面事實後追加否定補述，例如「選項取自所選項目，不需要猜」「系統會自動保存，不必手動儲存」
- 程式註解或文件以「本檔不處理」「本類別只負責」「不再使用」描述缺席狀態
- 技術文字出現「其實」「基本上」「確實」「真正」，拿掉後語意不變
- 敘事段落一句疊「一直非常」「習慣性地」「格外」這類修飾語，或只剩動作描寫，沒有作者的反應
- tooltip 或說明格只寫名詞片段，例如「語言欄位」「顯示名稱設定」
- 譯文保留原文語序，例如「對資料進行驗證的動作」「這個欄位是必要的」「資料會被驗證。」「It is the place where you can set...」
- 簡中出現「資料」「使用者」「預設」「建立」「設定」，或繁中出現「默認」「變量」「調用」「清零」
- 「必附」「皆為」「均須」「予以」這類公文腔
- 清單硬湊成三項，例如「創新、啟發與洞見」
- 同一實體在鄰近句子輪流稱為「服務」「模組」「元件」，或同一個名稱在同一份文件裡指兩件事
- 「首先」之後沒有「其次」，「一方面」之後沒有「另一方面」
- 「不需要設定檔」「結果會自動保留」等沒有主語的片段
- 敘事內容拆成「**效能**：……」「**安全性**：……」的條列
- 標題或條列前綴表情符號，「」與彎引號、直引號混用
- 中文句子出現「action != 保留」「spec + code」這類程式符號
- 正文留有「希望這對你有幫助」「需要我再補充嗎」
- 「根據現有資訊」「相關細節未公開」等免責聲明或臆測填空
- 「好問題！你說得完全對」等諂媚開場
- 「在這個時間點」「由於……的事實」等填充短語
- 「或許可以說有可能會產生一定程度的潛在影響」等疊加保留語
- 「未來一片光明」「令人期待的時代即將到來」等樂觀結尾
- 「真正的問題是」「從本質上來說」開場卻只是重述普通論點
- 「讓我們深入探討」「以下是你需要知道的」等宣告式開場
- 標題後接一句只重述標題的暖場句
- 文件或註解以「這是為了取代先前……而新增」敘述變更
- 連續三句以上的短促宣告句堆疊戲劇效果
- 「X 是 Y 的語言」「X 不是工具而是一面鏡子」
- 「說真的？」「老實說？」這類假裝坦率的停頓
- 「三大優勢」「分四個階段」「帶來三個改變：」這類只描述清單長度的數字
- 中文空話詞取代具體動作描述，例如「收斂」「賦能」「打通」「閉環」
- 「把結果端出來」「落檔」「掛上去」「把結果存。」這類讀者要猜意思的單音節動詞
- 「重查」「代寄」「改綁」「自檢」這類截短的複合詞，「起手搜尋式」這類沒有定義的自創術語
- 程式註解保留「原本」「先前」「此次」「新增」「改成」「移除」「目前」「暫時」「待補」「後續」等作業過程用語
- 一般樣式、互動、映射或資料流一律稱為「契約」，沒有指出正式 API、schema、相容性或治理來源

## 邊界

- 事實準確優先於文風。改寫只動修辭外殼，事實主張、數字與歸因保持原樣。
- 引用、標題、專有名詞與範例中出現的模式詞，是被討論的對象，寫在「」或 code span 內並維持原樣。
- 程式註解另依各語言的註解規範。
- 文件收錄位置、入口頁與 `.order` 維護依 [docs-entry-policy](references/docs-entry-policy.md)。
