# 文章人味校準

## 目的

讓文字讀起來像熟悉這個領域的人親手寫的。版面、標點、粗體與完整性由 Skill `/rule-documentation` 負責，本規則負責句子怎麼寫。

語言模型依統計挑選最可能出現的字詞，產出容易趨向平均值：同樣的句型、同樣的連接詞、同樣的補述習慣。本規則把這些平均值痕跡寫成可檢查的模式，並示範人會怎麼寫。

## 適用範圍

依文字的功能套用，同一份文件逐段判斷。使用者明確要求時，任何文字都套用全部章節：

| 文字類型 | 例子 | 套用範圍 |
|---|---|---|
| 敘事段落 | Launch Note、Feature Story、release note 的敘事段、proposal 與 case 說明動機與取捨的段落、部落格、隨筆 | 全部章節 |
| 技術文字 | 開發者文件、README、skill 檔案、JSDoc、TSDoc、Javadoc、行內與 HTML 註解、工具說明、表格說明格 | 核心原則、技術文體、語言與語法、填充與修辭腔、中文空話詞、交流殘留、風格 |
| 結構化參照 | 欄位字典、錯誤碼表的代碼欄、API schema、規格條款清單、code block、Mermaid 節點 | 依各自的規格維持中性精簡；其中的說明句仍套用技術文體 |

## 核心原則

1. **直接進入內容**：段落第一句就是資訊。開場暖場句、強調性的拐杖詞拿掉後，讀者更快讀到重點。
2. **同向陳述**：寫出事實，接著寫下一個事實。「不是 A，而是 B」、正面事實後追加的否定補述、戲劇性的分段鋪陳，都讓文章讀起來像套模板。
3. **句長有變化**：短句與長句交錯，清單的項數跟著內容走。每句長度與結構都相近，是統計平均值最明顯的痕跡。
4. **信任讀者**：直接陳述事實。軟化語氣、預先辯解與逐步引導，會讓讀者覺得被當成新手。
5. **具體勝過漂亮**：讀起來像能單獨截圖引用的金句，通常犧牲了精確度，改寫成具體陳述。

### 改寫保留資訊量

改寫覆蓋原文的全部內容。原文五段，改寫後仍是五段量級的資訊密度，拿掉的只有空洞修辭。

### 語氣校準

使用者提供自己的寫作樣本時，先讀樣本：留意句長、用詞層級、段落開場、標點習慣、慣用詞與過場方式，改寫時貼著樣本的語氣寫。樣本寫「東西」就寫「東西」，樣本寫短句就寫短句。沒有樣本時，敘事段落依下一節的預設語氣，技術文字依技術文體。

### 敘事段落的作者語氣

敘事段落背後要有一個真實的人。去掉 AI 痕跡之後，文字若變得整齊卻沒有聲音，讀者同樣認得出來。

作者在素材中表達過的觀點、猶豫與情緒，改寫時要寫出來：讓句子帶著作者對事實的反應，讓短句接一句需要時間展開的長句，保留離題、旁白與自我修正。觀點與第一人稱經驗只能來自作者已表達過的內容。

改寫前（整齊但沒有聲音）：

```text
這次實驗產生了有趣的結果。Agent 寫出了三百萬行程式碼。部分開發者印象深刻，部分則持保留態度。實際影響仍不明確。
```

改寫後（作者在場）：

```text
我真的不知道該怎麼看這件事。三百萬行程式碼，多半是在人類大概都睡了的時候產生的。開發社群一半人驚呼，另一半人在解釋為什麼這不算數。真相可能落在無聊的中間地帶，但我一直在想那些整夜運轉的 Agent。
```

## 模式型錄

各類模式的偵測訊號、成因與改寫前後對照，收錄在 [writing-patterns-catalog](references/writing-patterns-catalog.md)。改寫時依文字類型查對應分類：技術文字先查技術文體，敘事段落從內容模式查起。

## 驗收條件

改寫整篇敘事文章時，可以先寫草稿，自問「這段為什麼還像 AI 寫的」，列出殘留破綻後再定稿，完整流程示範見型錄的 [full-example](references/writing-patterns/full-example.md)。

交付的定稿達到下列條件：

- 每一處命中型錄模式的句子都已改寫，改寫後的句子沒有引入其他模式。
- 唸出來自然，句長有變化，用具體細節取代模糊主張，能用「是」「有」的地方就用「是」「有」。
- 全文沒有 `—`、`–`。
- 重讀一次，找不到一看就像 AI 寫的地方。

## 審查掛鉤

供文件審查時查閱。審查結論依本 skill 各章節與型錄逐項判斷，本節條目是查閱索引。

### 判定式

依「適用範圍」的文字類型逐段判斷，與檔案路徑無關。

### 反例列舉

- 句中出現「標誌著……關鍵時刻」「見證了……的演變」「彰顯其重要性」
- 句尾加上「……反映了團隊對品質的重視」這類補述式分析
- 非行銷文件出現「強大的」「無縫整合」「一站式」「極致體驗」
- 「業界普遍認為」「專家指出」卻沒有來源
- 文末出現「儘管面臨挑戰，仍持續發展」的收尾段
- 一段內疊用「此外」「至關重要」「值得注意的是」兩次以上
- 用「作為……的核心」取代「是」
- 「不是 A，而是 B」「不只是 A，更是 B」
- 正面事實後追加否定補述，例如「選項取自所選項目，不需要猜」「系統會自動保存，不必手動儲存」
- 「不處理 A，只負責 B」「只在儲存時檢查，不在輸入時檢查」
- 技術文字出現「其實」「基本上」「直接」「確實」「真正」，拿掉後語意不變
- 敘事段落一句疊「一直非常」「習慣性地」「格外」這類修飾語
- 敘事段落只剩動作描寫，沒有作者的反應
- tooltip 或說明格只寫名詞片段，例如「語言欄位」「顯示名稱設定」
- 譯文保留原文語序，例如「對資料進行驗證的動作」「It is the place where you can set...」
- 簡中出現「資料」「使用者」「預設」「建立」「設定」，或繁中出現「信息」「用户」「默认」
- 同一件事拆成三四個短句，例如「點擊儲存。系統驗證。驗證通過。資料寫入。」
- 清單硬湊成三項，例如「創新、啟發與洞見」
- 同一實體在鄰近句子輪流稱為「服務」「模組」「元件」
- 「不需要設定檔」「結果會自動保留」等沒有主語的片段
- 正文出現 `—`、`–`
- 以「；」或省略句號的換行連接兩個獨立陳述
- 句中把專有名詞或縮寫加粗
- 敘事內容拆成「**效能**：……」「**安全性**：……」的條列
- 標題或條列前綴表情符號
- 「」與彎引號、直引號混用
- 正文留有「希望這對你有幫助」「需要我再補充嗎」
- 「根據現有資訊」「相關細節未公開」等免責聲明或臆測填空
- 「好問題！你說得完全對」等諂媚開場
- 「在這個時間點」「由於……的事實」等填充短語
- 「或許可以說有可能會產生一定程度的潛在影響」等疊加保留語
- 「未來一片光明」「令人期待的時代即將到來」等樂觀結尾
- 「真正的問題是」「從本質上來說」開場卻只是重述普通論點
- 「讓我們深入探討」「以下是你需要知道的」等宣告式開場
- 標題後接一句只重述標題的暖場句
- 文件或註解以「這是為了取代先前……而新增」敘述變更
- 連續三句以上的短促宣告句堆疊戲劇效果
- 「X 是 Y 的語言」「X 不是工具而是一面鏡子」
- 「說真的？」「老實說？」這類假裝坦率的停頓
- 「三大優勢」「分四個階段」這類只描述清單長度的數字
- 中文空話詞取代具體動作描述（詞表見 [zh-buzzword](references/writing-patterns/zh-buzzword.md)）
- 「把結果端出來」「落檔」「掛上去」這類讀者要猜意思的單字動詞
- 程式註解以「本檔不處理」「本類別只負責」「不再使用」描述缺席狀態或修改歷程
- 程式註解保留「原本」「先前」「此次」「新增」「改成」「移除」「目前」「暫時」「待補」「後續」等作業過程用語
- 一般樣式、互動、映射或資料流一律稱為「契約」，沒有指出正式 API、schema、相容性或治理來源

## 邊界

- 版面、連字號、分號、粗體位置、標題分隔與完整性列舉，以 Skill `/rule-documentation` 為準。
- 圖、表、code block 與清單前後的段落關係，依 Skill `/rule-documentation` 的「產物與段落邊界」。
- 事實準確優先於文風。改寫只動修辭外殼，事實主張、數字與歸因保持原樣。
- 引用、標題、專有名詞與範例中出現的模式詞，是被討論的對象，維持原樣。
- 程式註解另依各語言的註解規範。
